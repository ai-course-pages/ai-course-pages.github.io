Pack a skill you will use again

A skill is a procedure written so a later chat can follow it without the transcript that produced it. A seed, from U1.S.2, carries one job's decisions. A compression or compaction, from U1.S.3, shortens the thread you are in. A skill carries a way of working you expect to repeat.

If these words are new

You can take this page once you can leave a chat with a short seed. The packing format below is the part that is new.

SKILL.md

The file many products know how to ingest is named SKILL.md. In the smallest case that file is the whole skill. The product reads it, and the procedure is available. Some contexts are built around that single file.

A skill can also arrive as a bundle. Beside SKILL.md, or in subfolders, you may find a short frontmatter block, often YAML. The block may be general, or it may be aimed at one model or one environment. You may also find reference notes, such as a README, other Markdown or plain-text files, and sometimes helper scripts. The bundle may be that folder, or a zip of it. Read SKILL.md first. Open a companion when the task needs a detail that was kept out of the standing rules.

When it applies

A skill should say when to use it and when not to, or it should name a trigger. That line keeps the procedure on the work it was written for. Without it, the skill can attach to a nearby task, and the chat spends tokens on the wrong steps.

Keep the standing rules short

Put the rules you want on every use in the short file. Put a long reference in a companion: a small frontmatter block when the extra facts are short, or a separate note when they are a page. The companion is read when the task needs it. A skill that pastes the whole reference into every turn spends like a thread that resends its dead ends.

Prefer that split when you have the choice. A short standing file plus a companion you can open is easier to carry to another product than one long file that assumes last year's chat window.

A product may notice a repeated procedure and suggest saving it as a skill. Treat that as a hint. Save it when you expect the procedure again. Leave it when the thread was a one-off. More about a skill the product already holds, and whether to add another, is on U1.K.2.

Finding a skill the product wrote

Inspecting that skill, exporting it, or referring to it from another chat can be less obvious than opening a file you saved yourself. Three places are worth trying. The product decides which of them exist.

  • A screen in the product. Some interfaces list skills, and from that list you can open one, export it, or point another chat at it.
  • The chat itself. Ask whether a skill you expect is present, and how to read it.
  • A folder on the machine. The product may have written the skill outside the project, in a place a non-technical reader would not think to open. The folder differs by product. Ask the product to name it, or use the screen above.

Suggested exercise

After a procedure you would want again, paste the first prompt. You are asking for a draft you can read. If the product has already written a skill in this session, paste the second prompt instead.

Turn the procedure we just used into a skill I can reuse in a later chat.

Write one SKILL.md. Include when to use it and when not to.
Keep the standing rules short. If a detail is long, name it as a companion note instead of pasting it into the standing rules.
Do not invent a second skill for the same job.
If this session already saved a skill, tell me how to inspect it, export it, or refer to it from another chat.
Say whether this product has a screen that lists skills.
If the skill is in a folder on this machine, name that folder in ordinary words.
