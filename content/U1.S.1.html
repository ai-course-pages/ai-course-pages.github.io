When a coding session should end

A coding CLI session is a thread that also runs tools. It gets more expensive the same way any long thread does: later steps resend the earlier ones. Two further choices are how large one automated request may be, and when the next job deserves a new session.

If these words are new

This page uses the thread and the usage window. A learner with little background would want these first.

  • U1.B.1 A follow-up resends the turns the product still keeps. A new chat does not.
  • U1.B.3 High effort is for a turn that must fit several earlier decisions. A check-in can be low.

A turn cap is a scope, not a token cap

Some automated runs accept a maximum number of turns. A turn is one step: the agent thinks, uses a tool, and continues. The cap says how far that single request may go before it stops and shows you the result.

  • A small cap fits a known edit. You want it to stop even if it has more ideas.
  • A larger cap fits a task that must touch several files before there is anything to read.

Hitting the cap is a stop. Read the files it wrote, then decide whether the next instruction belongs in that same session or in a new one. An interactive chat often has no such cap. The weekly usage meter is a different limit. A turn cap can fire while plenty of the weekly allowance remains.

When to open a new session

Open a new session when the durable result is already in files and the chat is mostly the trail that produced them. The clearest case is a section of several segments that holds together at this stage. The drafting thread has done its job. Carrying it forward makes every later step reread the dead ends.

Also open a new session when the next job is a different task, even in the same project, or when an automated run stopped at its turn cap and the next instruction is a new job.

Stay in the session when the next step needs an error, a diff, or a decision that exists only in the thread, or when the section is not coherent yet. Coherence is the test. A pile of segments is not enough.

What the new session needs

Pass paths, plus a short brief. Do not paste the old transcript.

  • Project folder. The directory the agent should read.
  • Entry point. The file a reader opens first, such as the page under test or the README.
  • Task artifact. The plan, the current segment, or a note of what was decided. One path for the task, not the whole history.

The new session reads those files. The old session can stay on disk. It does not have to be open.

Which folder the session may use

A path in the brief names where the work is. In a coding CLI, the session still needs that folder granted for this session. A new session does not keep the previous grant. When it asks, name the project folder the task needs. Add a second folder when the task truly reads both. A home directory, or a whole drive, pulls unrelated files into the turn.

A web chat has no project folder until you attach a file. That handoff is U1.S.2.
